# tln Language Specification — v0.2

This document is the canonical syntax + semantics reference for the
tln language as it exists in this repository today. It supersedes the
draft v0.1 specification in [#1](https://github.com/opentalon/tln-language/issues/1);
the deltas are summarised in the [Changes since v0.1](#changes-since-v01)
appendix.

Per-feature docs go deeper on individual subsystems and are linked from
each block section.

## Status

This specification matches the language implemented at the head of
master. The canonical grammar lives in
[`grammar.ebnf`](../../grammar.ebnf) and is the file the lexer / parser
target. Any disagreement between this document and the grammar is a bug
in this document.

---

## 1. Overview

tln is a domain-agnostic rule language designed to be:

- **Readable by humans** — domain experts can read, write, and audit
  rules without programming experience.
- **Deterministic** — every block's outcome is reproducible and
  traceable to the facts that triggered it.
- **Adaptive** — thresholds and parameters can be learned from each
  tenant's own data via the ML primitives and the ABC auto-tuning
  pathway.
- **Testable** — rules have their own test framework
  (`.tln.test` files).
- **Embeddable** — the runtime is a Go library; the CLI is a single
  static binary; the FactStore backend is pluggable.

tln files use the `.tln` extension; test fixtures use
`.tln.test`.

## 2. Architecture

```
.tln source
   └─→ Lexer → Parser → AST → Validator → Planner → []PlanStep
                                                       │
                                          ┌────────────┼────────────┐
                                          │            │            │
                                     FactQuery   GoComputation  MLComputation
                                          │            │            │
                                          ▼            ▼            ▼
                                   FactStore     render/optimize  ML runtime
                                   (Datalevin |
                                    MemoryStore)
```

- The planner emits structured `factstore.Query` values — not Datalog
  text. Every backend interprets the same structured form; the
  Datalevin client renders to wire-format Datalog at its boundary.
  See [`docs/factstore.md`](../factstore.md).
- `MemoryStore` is a Prolog-style in-process backend. The default for
  tests, the REPL, and `tln run --store=memory`.
- ML primitives (anomaly, learned threshold, predict, forecast,
  cluster, classify, similar, PPR) are Go-native; no external ML
  runtime required.

The compilation target is structured query plans against the FactStore
abstraction — not Prolog and not SQL. A different backend (Postgres,
custom `talon-db`) plugs in by satisfying `factstore.FactStore`.

## 3. File structure

A `.tln` file contains any number of top-level blocks in any order.
Recommended ordering for readability:

```tln
// helpers first
define "active" { ... }

// constraints next (run on every fact mutation)
constraint "Stock cannot be negative" { ... }

// policy rules
rule "..." { ... }
strict rule "..." { ... }

// detection / inference
detect "..." { ... }
forecast "..." { ... }
combine "..." { ... }
find related "..." { ... }

// reactive + workflows
on change attr "..." { ... }
workflow "..." { ... }

// recommendations close the loop
recommend "..." { ... }
```

The ordering is a convention, not a requirement.

## 4. Comments

```tln
// single-line

/* multi-line
   /* nested block comments are NOT supported */
*/
```

## 5. Values

| Kind     | Syntax                                                           |
| -------- | ---------------------------------------------------------------- |
| Number   | `42`, `3.14`, `-12`, `50000`                                     |
| String   | `"text"` — always double-quoted, supports `\"`, `\\`, `\n`, `\t` |
| Boolean  | `true`, `false`                                                  |
| Duration | `7 days`, `30 days`, `12 weeks`, `1 year`, `20000 km`            |
| List     | `["a", "b", "c"]`, `[100, 200, 300]`                             |

Duration units: `days`, `weeks`, `months`, `years`, `km`.

## 6. Operators

| Category   | Operators                          |
| ---------- | ---------------------------------- |
| Comparison | `==`, `!=`, `<`, `<=`, `>`, `>=`   |
| Arithmetic | `+`, `-`, `*`, `/`, `%`            |
| Logical    | `and`, `or`, `not`                 |
| Membership | `in [...]`, `not in [...]`         |
| String     | `contains`, `starts_with`, `ends_with` |
| Temporal   | `older_than`, `newer_than`         |
| Pattern    | `is anomaly compared_to last N days` |

## 7. Expressions

```tln
attr "km"                          // attribute reference
item.name                          // bare identifier on the matched record
context.role                       // runtime context variable
today                              // current date
now()                              // current date-time (today is date-only)
date("2026-07-01")                 // coerce a string to a date value
days_until(attr "due_on")          // whole days from today, as a number
days_between(attr "a", attr "b")   // whole days from a to b, as a number
category_tree("Vehicles")          // recursive category descendants
learned_threshold p95 of attr "x" over last 90 days   // ML-derived threshold
total(attr "price")                // aggregate (only inside combine subject_to)
step("create_person").result.id    // step result reference (workflow / on)
list.map(field)                    // extract field from each element of a list
```

Aggregates (`total`, `count`, `avg`) inside expressions are restricted
to `combine` block `subject_to` clauses today; the template-string form
(`"{total(attr.price)} EUR"`) is tracked under
[the template-functions follow-up](#changes-since-v01).

## 8. Selectors

A selector filters which records a block operates on. Every block that
runs against the FactStore (rule, detect, recommend, combine, on,
constraint, predict, forecast, cluster, classify, find similar/related)
starts with one.

```tln
for records where type == "item"
  and status == "active"
  and attr "km" > 20000
  and category in category_tree("Vehicles")
  and is "high_value"            // reference a define block
  and attr "region" == context.region
```

`type`, `status`, and `category` are first-class record keys.
Everything else is an attribute and uses the `attr "name"` form.

## 9. Templates

String templates use `{...}` for interpolation. Today's interpolation
recognises bare references against the matched record:

```tln
label "{item.name}: {attr.km} km since service"
reason "Provider {attr.provider_id} on the blacklist"
suggest "Order {attr.minimum_amount} bags of {item.name}"
```

Template **function** interpolation (`{count}`, `{total(attr.x)}`,
`{days_until(date)}`) is a v0.2 gap — see
[the follow-up issue](#changes-since-v01).

## 10. Context

`context` carries runtime values supplied by the caller. The host
(OpenTalon, an SDK consumer, the REPL) injects them at evaluation time;
the tln source never declares them.

```tln
context.user
context.role
context.region
context.entity
context.selected_features
context.<any-key>
```

Reference inside selectors and templates: `context.role`, `context.entity`,
etc.

## 11. Priority

Four levels. Used by detect, rule, recommend, combine, and the ML
blocks. Also used by the defeasible conflict resolver to disambiguate
rules that match the same target.

```
LOW < MEDIUM < HIGH < CRITICAL
```

Rules without an explicit `priority` clause default to `MEDIUM`.

## 12. Block reference

tln has thirteen top-level block types. The grammar's canonical
production for each is in [`grammar.ebnf`](../../grammar.ebnf); this
section gives intent + minimal example.

### 12.1 `define`

Reusable named conditions. A define block has no side effects on its
own; other blocks reference it with `is "name"`.

```tln
define "active" {
  status == "active"
}

define "due_for_service" {
  attr "km" > attr "last_service_km" + 20000
}

define "covers" (features) {
  for each f in features {
    attr f == true
  }
}
```

### 12.2 `rule`

Enforces a constraint on an action. Returns block / allow / requires, and/or a
list of `do` actions for the host to carry out — see
[`docs/actions.md`](../actions.md).

```tln
rule "No assignment during maintenance" {
  for records where type == "item"
    and has record type "maintenance_ticket"
  before "assign"
  block "assign"
  reason "Item has an open maintenance ticket"
  priority HIGH
}

rule "Regional restriction" {
  when tool_action starts_with "inventory"
    and context.region != attr "region"
  block reason "Not available in your region"
}
```

`strict` and `overrides` give rules defeasible reasoning — see
[`docs/defeasible.md`](../defeasible.md).

```tln
strict rule "Expired certification blocks assignment" { ... }

rule "Cleanup crew can delete" {
  when tool_action contains "delete"
  overrides "Block all deletions"
  allow "delete"
  priority HIGH
}
```

### 12.3 `detect`

Finds patterns in data. Returns matching record IDs + a label per
match.

```tln
detect "Service overdue" {
  for records where type == "item"
    and status == "active"
    and attr "km" > attr "last_service_km" + 20000
  flag matching items
  label "{item.name}: {attr.km - attr.last_service_km} km since service"
  priority HIGH
}
```

Pattern expressions (`3+ records same category`, `record type A
followed_by record type B`) are out of scope for v0.2 — tracked under
the [follow-up issue](#changes-since-v01) for sequence patterns.

**Provenance annotations.** Auto-discovered rules can carry the
generator's self-asserted confidence + a free-form provenance string.
Both are optional and surfaced verbatim in `tln explain` output.

```tln
detect "auto-discovered: External Workshop correlation" {
  for records where category == "van"
  flag matching items
  confidence 0.82
  source "mined from 14 months of data, 47 matching cases"
}
```

`confidence N` (no `>=`) is the provenance form and lives on the
detect / rule block as a self-annotation. The existing `confidence
>= N` filter for ML primitives is unchanged — the parser disambiguates
by the next token. Score is range-checked to `[0, 1]` by the validator.

### 12.4 `recommend`

Suggests an action when a condition or detect block matches.

```tln
recommend "Order cement" {
  when detect "Cement running low" matches
  calculate avg_weekly from activities
    where type == "consume" within last 30 days
  suggest "Order {avg_weekly * 4 - attr.current_stock} bags"
  priority HIGH
}
```

`suggest` is a template-string action. The v0.1 spec's
`action create_record / notify` vocabulary was replaced by the simpler
template form; downstream MCP calls handle the actual side effects
(see `workflow` and the `remediate` follow-up in #17).

### 12.5 `combine`

Multi-objective combinatorial optimisation. Five backends (Pareto, GA,
ACO, ILP, plus auto). See
[`docs/optimizers/README.md`](../optimizers/README.md).

```tln
combine "Dispatch picks" {
  for records where is "dispatchable"
  minimize attr "cost_per_km"
  maximize attr "urgency_score"
  return id, cost_per_km, urgency_score
  label "Dispatch {item.name}: cost {attr.cost_per_km}, urgency {attr.urgency_score}"
  priority HIGH
}

combine "Parts reorder" {
  for records where type == "stock_item"
  select 5 from records
  minimize total(attr "price")
  subject_to total(attr "price") <= 5000
  return id, price
}
```

### 12.6 `workflow`

Multi-step MCP orchestration. Steps name their dependencies with
`depends_on`; results flow via `step("name").result.field`.

```tln
workflow "Onboard employee" {
  step "create_person" {
    tool "hr" "create-person" {
      first_name context.first_name
      last_name context.last_name
    }
  }

  step "assign_equipment" depends_on "create_person" {
    tool "inventory" "assign-item" {
      item_id context.laptop_id
      person_id step("create_person").result.id
    }
  }

  step "notify_manager" depends_on ["assign_equipment"] {
    tool "notifications" "send" {
      channel context.manager_channel
      message "{context.first_name} onboarded"
    }
  }
}
```

See [#17](https://github.com/opentalon/tln-language/issues/17) for the
MCP interface RFC and the follow-up issues (#53–#58) for the
remediate/enrich/error-handling extensions.

### 12.7 `on` (reactive)

Fires when a fact mutates — without polling. See
[`docs/reactive.md`](../reactive.md).

```tln
on change attr "current_stock" {
  when new_value <= record.attr "minimum_amount"
  logger.warn "Stock threshold crossed: {item.name}"
  recommend "Order stock"
}

on assert activity {
  detect "Defective item without ticket"
}

on retract item {
  logger.warn "item removed: {event.entity}"
}
```

Body actions: `logger.<level> "template"`, plus block references
(`recommend "name"`, `detect "name"`).

### 12.8 `constraint`

Integrity constraints checked on every fact mutation. See
[`docs/constraints.md`](../constraints.md).

```tln
constraint "Item status is valid" {
  for records where type == "item"
  require attr "status" in ["active", "defective", "missing", "inactive"]
  on_violation reject "Invalid status: '{status}'"
}

constraint "Stock cannot be negative" {
  for records where type == "stock_item"
  require attr "current_stock" >= 0
  on_violation reject "Stock cannot be negative"
}
```

Violation modes: `reject` (refuse the fact), `warn` (accept + log),
`quarantine` (route to a separate sink).

### 12.9 `predict`

Decision-tree-style classification primitive.

```tln
predict "Engine failure risk" {
  for records where type == "vehicle"
    and status == "active"
  features [attr "km", attr "engine_temp", attr "vibration_score"]
  trained_on records where type == "vehicle"
    and attr "had_failure" == true
  confidence >= 0.8
  label "{item.name}: {confidence}% risk"
  priority HIGH
}
```

### 12.10 `forecast`

Exponential-smoothing time series forecast.

```tln
forecast "Cement stock-out" {
  for records where type == "stock_item"
    and attr "name" == "Portland Cement"
  series attr "current_stock" over last 30 days
  predict days_until value <= 0
  when days_until < 7
  label "{item.name}: out in ~{days_until} days"
  priority CRITICAL
}
```

### 12.11 `cluster`

DBSCAN clustering. Returns each row's cluster id.

```tln
cluster "Failure modes" {
  for records where type == "incident"
  by attr "duration", attr "severity"
  label "Cluster {cluster_id}: {count} incidents"
}
```

### 12.12 `classify`

K-nearest-neighbour classification.

```tln
classify "Customer segment" {
  for records where type == "customer"
  features [attr "annual_spend", attr "tenure_months", attr "support_tickets"]
  confidence >= 0.7
  label "{item.name} → {predicted_class}"
}
```

### 12.12a `decide`

Typed decisions: a calibrated probability distribution over a fixed `choices`
set, plus the argmax `chosen` and its `confidence`. Deterministic mode reuses
kNN and exposes the full distribution; model mode delegates to an injected
`ToolResolver` (a Jev / laya System-1 model). See
[`docs/decide.md`](../decide.md) and
[`docs/design/0014-decide-typed-decisions.md`](../design/0014-decide-typed-decisions.md).

```tln
decide "email_kind" {
  for records where folder == "Inbox"
  choices ["Legitimate", "Spam", "Phishing"]
  ask concat("Subject: ", attr "subject", "\n\n", attr "body")
  using model "jev-small"
  confidence >= 0.9
}
```

### 12.13 `find similar` / `find related`

Two retrieval primitives. `similar` is cosine over an attribute set;
`related` is Personalised PageRank over the fact graph. See
[`docs/design/0002-ppr-fact-graph.md`](../design/0002-ppr-fact-graph.md).

```tln
find similar "Comparable parts" {
  for records where type == "part"
  to attr "id"
  within 0.2
}

find related "Connected vehicles" {
  for records where type == "vehicle"
  seeds [context.recent_failures]
  top_k 5
  damping 0.85
}
```

### 12.14 Tuning ML blocks against a fixture

Any ML block can carry a `tune against test "FixtureName"` clause that
asks the planner to auto-tune the primitive's parameters via
Artificial Bee Colony optimisation. See
[`docs/optimizers/abc-tuning.md`](../optimizers/abc-tuning.md).

```tln
detect "Unusual consumption" {
  for records where type == "stock_item"
  is anomaly compared_to last 12 weeks
  flag matching items
  tune against test "Consumption fixture"
}
```

### 12.15 `connector`

Binds a tool-server name to the plugin that backs it, so a program can name its
external dependencies in source (ADR 0012). A `tool "<name>" …` call routes to
the connector's plugin.

```tln
connector "inventory" via mcp {
  endpoint env "INVENTORY_URL"
  bearer   env "INVENTORY_TOKEN"
}
connector "audit" via io { path "/var/log/tln/audit.log" }

tool "inventory" "list-items" { query "x" }   // → the mcp plugin
tool "audit" "writeln" { text "overdue: {item.id}" }
```

`via <plugin>` names the backing plugin; the block body is free-form `key value`
config the plugin interprets (`endpoint`/`bearer` for mcp, `path`/`stream` for
io). **`env "VAR"`** resolves a value from the environment at run time and is
valid **only** inside connector config — the general expression grammar rejects
it, so a secret can never reach a label, a stored fact, or a tool argument.
Resolution is deny-by-default: absent a host env resolver, `env` fails.

Routing is two-mode: a host-installed tool resolver handles every call;
otherwise connectors are consulted (loaded via their registered plugin factory —
see §14.1, `mod.tln`); otherwise the call errors.

## 13. Tests (`.tln.test` files)

Companion files exercise blocks against scripted fact fixtures. See
[`docs/repl.md`](../repl.md) for the REPL counterpart.

```tln
test "Active items detection" {
  given {
    record 501 type "item" status "active"
    attr 501 "name" "VW Transporter"
    attr 501 "km" 45000
  }
  when detect "Service overdue"
  expect {
    flagged 501
  }
}
```

Supported assertions: `flagged ID`, `not flagged ID`, `count == N`,
`label contains "..."`, `priority == HIGH`.

CLI: `tln test [paths...] [-run NAME] [-v] [--junit FILE]`.

## 14. CLI surface

| Command          | Purpose                                                        |
| ---------------- | -------------------------------------------------------------- |
| `tln build`    | Compile `.tln` files, report diagnostics, print plans.       |
| `tln test`     | Run `.tln.test` files. JUnit export with `--junit`.          |
| `tln run`      | Execute a program; non-bundled runs use the in-memory store. |
| `tln trace`    | JSON per-step trace of `.tln.test` execution.                |
| `tln explain`  | Tier-1 explainability — Decision chains. `--csv` / `--json`.    |
| `tln repl`     | Interactive REPL ([`docs/repl.md`](../repl.md)).               |
| `tln init`     | Scaffold a project: `<name>/mod.tln` + `rules.tln`.            |
| `tln bundle`   | Compile the plugins in `mod.tln` into a project-local binary.  |
| `tln version`  | Print the binary's version string.                              |

Global flags: `--log-format=text|json`, `--log-level=debug|info|warn|error`.

### 14.1 Project manifest (`mod.tln`) and bundling (ADR 0013)

A project declares the plugins it uses in `mod.tln`, Bundler-style (one line per
plugin, `//`/`#` comments):

```tln
plugin "mcp"    "v0.1.0"                              # → github.com/opentalon/tln-mcp
plugin "io"     "v0.1.0"
plugin "acme"   "v1.2.0" from "github.com/acme/tln-acme"   # third-party source
plugin "db"     "v0.9.0" store                        # a FactStore plugin
```

Go cannot load Go code at run time without a dependency cycle (core must never
import a plugin), so `tln bundle` **generates and compiles** instead of loading:
it writes a project-local bootstrap module under `.tln/bundle/` that imports core
plus each declared plugin and registers its `Factory` via `tln.WithPlugin`, then
`go build`s a project-local `tln` binary and writes `mod.lock`. `tln run` then
re-execs that binary, so a `connector "…" via <name>` block resolves with no Go
in the user's project:

```bash
tln init demo && cd demo
tln bundle          # like `bundle install`
tln run rules.tln   # connectors resolve to the bundled plugins
```

A Go toolchain is required for `tln bundle`.

The **backing store** is chosen Active-Record style — by config, defaulting to
in-memory. A `store` plugin in `mod.tln` plus a `config/store.tln` selects it:

```tln
# config/store.tln — env resolves at run time; no file → in-memory
store db {
  target env "TLNDB_ADDR"        # e.g. unix:///tmp/tlndb.sock
}
```

Precedence: an explicit host `WithFactStore` > the `store` plugin + `config/store.tln`
> the in-memory default. At most one `store` block. Tool plugins wire via
`WithPlugin`; the store wires via `WithFactStore`. (A sidecar store like tln-db
still runs its server separately; the bundle carries only the client.)

## 18. Changes since v0.1

The v0.1 draft was a forward-looking design document; v0.2 documents
what shipped. The substantive deltas:

### Compilation target

- v0.1: "Compiles to Prolog → Trealla Prolog (WASM)."
- v0.2: Compiles to structured `factstore.Query` against a pluggable
  FactStore. Datalevin and MemoryStore are the two shipped backends.
  No Prolog, no Trealla.

### Block types

- v0.1: 5 block types — define, rule, detect, recommend, combine.
- v0.2: 13. Added workflow, on, constraint, predict, forecast, cluster,
  classify, find similar, find related. Each carries its own RFC and
  per-feature doc.

### `recommend` actions

- v0.1: `action create_record { ... }`, `notify role "x" { ... }`.
- v0.2: `suggest "template"`. Side effects are delegated to `workflow`
  blocks and (soon) inline `mcp` calls via the
  [`remediate` follow-up](https://github.com/opentalon/tln-language/issues/53).

### `combine` syntax

- v0.1: `need features [...]`, `compare single vs bundle`, `show
  savings`, `where total ... < N`.
- v0.2: `minimize` / `maximize` / `select N from records` /
  `subject_to total(attr "x") <= N` / `return id, x, y`. Five optimizer
  backends ([`docs/optimizers/`](../optimizers/README.md)).

### Rules

- New: `strict` modifier; `overrides "name"` clause. See
  [`docs/defeasible.md`](../defeasible.md).
- New: priority-based conflict resolver with tie warnings
  (`internal/defeasible`).

### Detect

- New: `is anomaly compared_to last N days` clause routes through ML
  primitives (z-score, Grubbs).
- New: `tune against test "Fixture"` clause for ABC auto-tuning of ML
  parameters (`docs/optimizers/abc-tuning.md`).

### New cross-cutting features

- **Templates** — bare-identifier interpolation against the matched
  record. Function interpolation (`{count}`, `{total(...)}`) is
  [tracked](https://github.com/opentalon/tln-language/issues/) as a
  v0.3 gap (see next section).
- **Test framework** — `.tln.test` files with `given` / `when` /
  `expect`, runnable via `tln test`.
- **Trace + Explain** — `tln trace` (per-step JSON) and
  `tln explain` (Tier-1 Decision chains, ADR-0003).
- **REPL** — `tln repl` with `:eval`, `:trace`, `:find`, `:load`
  (`docs/repl.md`).
- **Observability** — structured logging via `--log-format=json`, MCP
  call events, executable `on { logger.warn "..." }`
  (`docs/observability.md`).
- **FactStore abstraction** — pluggable backend; MemoryStore ships
  alongside Datalevin (`docs/factstore.md`).

### Removed from v0.1 vocabulary

These v0.1 keywords are **not** reserved in v0.2 because they were
never wired up: `approaching`, `cheaper_option_exists`, `has_open`,
`has_expired`, `savings`, `single`, `bundle`, `compare`, `vs`, `show`,
`create_record`, `update_record`, `notify`.

The first three (`approaching`, `has_open`, `has_expired`) are
candidates for v0.3 sugar over patterns tln can already express; see
the gap issues.

### Genuine v0.1 gaps tracked for v0.3

These v0.1 features remain useful and are tracked as separate issues:

- **`version` file declaration** — enforces forward-compat.
- **Template function interpolation** — `{count}`, `{total(attr.x)}`,
  `{days_until(...)}` etc. in label / reason / suggest strings.
- **Sequence patterns in detect** — `record type A followed_by record
  type B on same item within 30 days`.
- **`has_open` / `has_expired` / `approaching` sugar** — over patterns
  tln can already express via temporal + selector composition.

See [the gap issues](https://github.com/opentalon/tln-language/issues?q=is%3Aopen+label%3Aspec-gap) for status.
